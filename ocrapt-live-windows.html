Before we start

The paper doesn't run live. Our demo does.

Everything after this slide is about the gap between these two pictures.

PaperOffline, whole log

Inference "processes provenance graphs containing both benign and malicious traces" (§5.1.3). Table 3 reports 59.21 s and 10.48 GB for host W10: that is one batch pass over the full test log, not a per-event latency.

OursMicro-batch over windows

The same pipeline, executed over and over on recent data. Each execution is called a run. This is an adaptation, so our numbers are not comparable to the paper's (data, labels and inference mode all differ).

Part 1 of 3: one run

What happens in one detection run

A run is one pass through the seven stages below: read recent events, score them, maybe raise an alert. The demo starts a run at fixed minutes, and we name each run by the minute it starts, written $t$: "the run at 10" is the one that starts at minute 10. To keep it simple, for now: a run every 5 minutes (at 5, 10, 15), each reading only the 5 minutes before it. Part 3 explains why you might run more often.

  1. Collect events
  2. Build graph
  3. Featurize
  4. Score nodes
  5. Threshold
  6. Grow subgraphs
  7. Alert

The whole run in one line

Take the last $w$ minutes of audit events, turn them into a graph, score every node, keep the clearly abnormal ones, and connect them into small attack stories.

1. Collect all events in $[t - w,\ t)$

Here $w = 5$ min. "[" includes the start, ")" excludes the end.

Runs happen at minute 5, 10, 15, and each starts its window 5 minutes earlier, so start $= t - 5$:
  • run at $t = 5$: $[5 - 5,\ 5) = [0, 5)$, events from 00:00 up to 04:59
  • run at $t = 10$: $[10 - 5,\ 10) = [5, 10)$, events from 05:00 up to 09:59
An event at exactly 05:00 is not in the first run; it belongs to $[5, 10)$.

2. Build the provenance graph for this window

Nodes are processes, files and sockets; edges are actions (start, write, connect) with timestamps. OursNode IDs are prefixed with the window, so each window is an independent graph.

edge_index [2, E_t] edge_type [E_t]

3. Compute behavior features per node

PaperAction counts plus idle-period statistics (min, max, mean gap between actions), §5.1.2. Ours12 L2-normalised action counts and 3 min-max idle stats, scaled with the scaler frozen from training.

X_t ∈ ℝ^(N_t × 15)

4. Score each node with its type's OCRGCN

PaperOne model per node type (process, file, socket). Each is an RGCN, so messages flow over typed edges from all neighbor types; it learns a hypersphere around normal embeddings (§5.1). A node's score grows the further it sits outside that normal region.

scores ∈ ℝ^(N_type) one number per node

5. Keep nodes above the threshold

PaperA node is anomalous when its score exceeds the pre-computed threshold for its type (§5.1.3): $s_i > \tau_{\text{type}}$. Most nodes stay normal.

With an illustrative $\tau_{\text{process}} = 0.80$:
  • powershell.exe scores 0.91: $0.91 > 0.80$, anomalous
  • winword.exe scores 0.41: $0.41 \le 0.80$, normal
Files and sockets have their own thresholds, because each type has its own model.

6. Grow anomalous subgraphs (Alg. 1)

A hop is one edge, followed in either direction. A node's one-hop neighbours are the nodes linked to it by a single edge.

If powershell.exe is anomalous:
  • winword.exe started it, so winword is one hop away
  • explorer.exe started winword, so explorer is two hops away (explorer → winword → powershell)

PaperAlg. 1 (§5.2, Fig. 3) links anomalous nodes that share an edge, adds their one-hop neighbours, keeps only the neighbours that lead to another anomalous node, then drops subgraphs with a low overall score. That last filter is where much of the precision comes from (Table 4, "Without SG-Det"). Part 2 walks through it on an example.

7. Emit the subgraph as the alert

The analyst gets a handful of nodes and edges with timestamps. Optionally, the LLM investigator (Alg. 2) turns it into a written report, but that can run asynchronously after the alert.

Part 2 of 3: what gets flagged

Nodes get scored, subgraphs get alerted, the window never does

Common mistake

If something inside the 5-minute window scores as anomalous, the whole window is the alert.

Which window is this?

Reminder: a run is one pass of the seven-stage pipeline from part 1, started at a fixed minute. Runs start at minute 5, 10, 15. The attack chain happens between 06:30 and 07:40, so it lands in the run at minute 10.

Each run looks at the 5 minutes before it:
  • run at 5: $[0, 5)$, ends before the chain starts
  • run at 10: start $= 10 - 5 = 5$, so $[5, 10)$, 05:00 up to 09:59, contains 06:30 to 07:40

One window, nine nodes

Circles are processes, squares files, diamonds sockets. Step through to see what the model produces.

1. Every node gets its own score

OCRGCN outputs one number per node. There is no "window score".

2. Three nodes cross $\tau$

powershell (0.91), rundll32 (0.94) and the external socket (0.86). a.dll scores 0.62, below its threshold. The other six nodes are normal.

3. Look one hop around them

A hop is one edge, in either direction. Alg. 1 collects every node one edge away from an anomalous node (blue dashed).

  • powershell: winword started it, it wrote a.dll, so both are one hop away
  • rundll32: it loaded a.dll, so a.dll is one hop away from it too
explorer is two hops from powershell, so it isn't considered.

4. Keep only neighbours that lead to another anomaly

  • a.dll: kept. It sits between two anomalous nodes (powershell wrote it, rundll32 loaded it), so it connects the story.
  • winword: dropped. Beyond powershell it only reaches explorer, which is normal: a dead end.

Correct reading

The alert is a small subgraph: these nodes, these edges, at these times. PaperThis is the point of OCR-APT versus window-level detectors such as KAIROS, which flag an entire time window and leave the analyst to search it. Context the pruning dropped (here, that Word started PowerShell) is still in the graph for the analyst or the LLM step to query.

Part 3 of 3: stride and window

Two knobs. So far, both were 5 minutes.

Everything until now assumed one simple setup. Here it is, named.

Window $w$: how far each run looks back

So far $w = 5$. It must match the window used in training.

  • run at 10, $w = 5$: sees $[5, 10)$
  • run at 10, $w = 10$: would see $[0, 10)$

Stride $s$: how many minutes between runs

So far $s = 5$. The window moves forward by $s$ each run.

  • $s = 5$: runs at 5, 10, 15
  • $s = 2$: runs at 5, 7, 9, 11

With $s = w$ the windows sit end to end: no overlap, no gap. These are called tumbling windows.

For our small demo, this is enough

We control when the attack runs, and an Atomic Red Team test lasts seconds. Start it just after a boundary and the whole chain lands in one window.

What it saves

  • Each event is in exactly one window, so it's processed once.
  • One attack gives one alert: no duplicate alerts, no dedup logic.
  • Only 12 runs per hour.

Part 3 of 3: stride and window

Real attacks don't wait for the boundary

An attacker doesn't know where our windows start. Take the same chain as in part 2, but starting at 04:30 instead of 06:30. Now it crosses minute 5.

The chain

1 04:30 winword → powershell (start)
2 05:10 powershell → a.dll (write)
3 05:25 powershell → rundll32 (start)
4 05:40 rundll32 → 203.0.113.7:443

What each tumbling window sees

[0, 5): only Word starting PowerShell. Suspicious, maybe not enough.

[5, 10): a different node, w2:powershell, with no parent. A DLL write and a connection, but without the Office origin.

Why the cut hurts this model

  • Features are per-window counts: each half-node has half the behavior.
  • Message passing only uses edges in the same graph, so rundll32 never "sees" winword.
  • Alg. 1 can't join two windows, so we get two weak half-stories that the subgraph filter may drop.

Idea: what if each window overlapped the previous one, so a chain near a boundary still fits whole in some window? Next slide.

Part 3 of 3: stride and window

The fix: run more often than the window is long

Keep $w = 5$, but set $s = 2$: a run at 5, 7, 9, 11, each still looking at the 5 minutes before it. Neighbouring windows now share $5 - 2 = 3$ minutes. These are called sliding windows.

Window $w$: unchanged

Still 5 min, still start $= t - 5$. Only the run times changed.

  • run at 7: $[7 - 5,\ 7) = [2, 7)$
  • run at 9: $[9 - 5,\ 9) = [4, 9)$

Stride $s$: now 2

Runs every 2 minutes instead of 5. Worst-case alert delay is about $s + t_{\text{proc}}$.

With $s = 2$ (runs at 7, 9, 11):
  • event at 07:01: first seen by the run at 9, about 2 min wait
  • event at 08:58: also the run at 9, about 2 s wait
Plus processing time $t_{\text{proc}}$ in both cases.

Overlap $w - s$

When $s < w$, windows overlap and each event is processed $w/s$ times on average ($5/2 = 2.5$ here). That's the price.

With $w = 5,\ s = 2$:
  • chain start, 04:30: in $[0, 5)$, $[2, 7)$, $[4, 9)$, so 3 times
  • chain end, 05:40: in $[2, 7)$, $[4, 9)$, so 2 times

OursTraining can use its own stride: slicing the benign capture with $s = 2$ gives more training windows. Only $w$ has to match between training and inference.

Part 3 of 3: stride and window

Back to the cut chain: overlap keeps it whole

Why the run at 7 catches it

  • window start $= 7 - 5 = 2$, so $[2, 7)$ is 02:00 up to 06:59
  • the chain runs 04:30 to 05:40, entirely inside it
The run at 9, $[4, 9)$, also contains it, so the same attack will show up twice. That's why sliding needs dedup.

What overlap guarantees

Any activity of duration $d \le w - s$ fits entirely inside some window. With $w = 5,\ s = 2$: $d \le 5 - 2 = 3$ minutes. With tumbling windows, $w - s = 0$: any chain can be cut.

  • 3-min chain, 05:30 to 08:30: fits in $[4, 9)$, intact
  • 4-min chain, 05:30 to 09:30: $[4, 9)$ ends too early, $[6, 11)$ starts too late, so it is cut

Part 3 of 3: stride and window

Feed the whole window, not just the new minutes

Common mistake

With sliding windows, a run happens every 2 minutes, so take only those 2 new minutes, encode them, and score them.
Same rule for every run:
  • run at $t = 9$: tempting slice $[7, 9)$, correct window $[4, 9)$
  • run at $t = 11$: tempting slice $[9, 11)$, correct window $[6, 11)$

Why it breaks

The model and the feature scaler were fit on 5-minute windows. A 2-minute slice has smaller action counts and idle gaps capped at 120 s, so its features come from a different distribution. Nodes look odd because the input is odd, not because of an attack.

Rule

The inference window must equal the training window. Stride only decides when the next run starts; each run still looks back the full $w$.

If you slide, deduplicate

The same malicious rundll32 will be flagged in consecutive runs. Strip the window prefix and key alerts on a stable identity: image + PID + start time for processes, path for files, IP:port for sockets.

What no stride can fix

  • Chains longer than $w - s$ (3 min here) can still get split.
  • History older than $w$ is invisible: a parent started 20 min ago has no edge in the window.
  • A beacon every 10 min shows up as one lone connection per 5-min window; its long idle gaps can't be measured.

What we can honestly claim

A windowed, micro-batch adaptation of OCR-APT's detector that can catch short, contained attack chains, validated offline on our own labeled capture first. Not long multi-stage campaigns, and not comparable to the paper's W10 results.

Check yourself

Five questions before you touch the demo

Answer in your head first, then open each one.

1. With $w = 5$, which events go into the run at minute 9? Why not only minutes 7 to 9?

Everything in $[4, 9)$. Using only the newest 2 minutes shrinks counts and caps idle gaps, so the features no longer match the 5-minute training distribution.

2. What does the analyst receive when a run finds an attack?

A small subgraph: the anomalous nodes, the normal nodes Alg. 1 used to connect them, and the edges with timestamps. Never "this window is anomalous".

3. With $s = 2$, a malicious rundll32 is flagged at minutes 7 and 9. How many alerts should reach you?

One. Both copies are the same process once the window prefix is stripped; key on image + PID + start time and merge.

4. Switch to tumbling ($s = 5$). What happens to alert delay, chain coverage, and training windows from a 20-minute capture?

Delay rises to about 5 min, no chain is guaranteed intact, and training windows drop from $\lfloor (20-5)/2 \rfloor + 1 = 8$ to $\lfloor (20-5)/5 \rfloor + 1 = 4$ (unless training keeps its own smaller stride).

5. Keep $s = 2$ but raise $w$ to 10. Longest guaranteed chain? Times each event is processed?

$w - s = 10 - 2 = 8$ min, and $w/s = 10/2 = 5$ times. More context and coverage, paid for with more compute and more duplicates, and the model must be retrained on 10-minute windows.
