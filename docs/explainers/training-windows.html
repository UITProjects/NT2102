Twenty minutes of benign activity, cut into five-minute graphs

How the OCRGCN trainer in this project uses the benign capture: why the 20-minute recording is sliced into overlapping 5-minute windows, why two of them are thrown away, how all windows end up in one graph without mixing, and why the idle-time features make the window length matter.

Numbers come from the benign experiment 20261009T145632Z and training run exp01 (docs/PROGRESS.md). A wider recapture is under way, so the counts will change; the mechanism will not. 220 minutes is the raw material, 5 minutes is the sample

"So what about 20 minutes? Is it useless?"

The 20 minutes is how much benign activity you record. The 5 minutes is the size of each piece the model sees. The recording length decides how many pieces you get. 20 is simply the default of the workload script (06-benign-workload.ps1:30, [int]$DurationMinutes = 20), not a number from the paper.

OURS The rule (etwwindow.py:15-18, :70-78): window k starts at k × stride and covers [start, start + window), meaning from start up to but not including start + window. Only full windows are kept. Move the sliders.

3One event lands in several windows

Windows overlap, so the windower copies each event into every window whose [start, start + 5) contains it (window_ids_for, etwwindow.py:81). With window 5 and stride 2, that is at most ⌈5 / 2⌉ = 3 windows (⌈x⌉ means round up). This is why 37,294 edges become 68,319. Drag the event along the capture.

4Why two windows are purged

"Why are 2 purged and not used for training?"

Validation asks one question: does the model leave benign activity it has never seen unflagged? That check is only honest if the validation window shares no events with training. Overlapping windows do share events, so training on them would be like handing out the exam answers before the exam.

OURS make_split (train_gnn_models.py:130-157) holds out the last window and purges the ⌈window / stride⌉ − 1 windows before it (--purge-windows 2, :390). The paper does not describe this, because it does not use sliding windows. Click any window to hold it out and see who overlaps it.

Why not move the two overlapping windows into validation instead? Because they overlap training on their other side: w0005 [10, 15) shares minutes 10–13 with w0004 [8, 13). The leak would just move. Cutting them out is the clean break.

INFERENCE Holding out the last window rather than a middle one means only one side needs purging (try clicking w0003 above: four neighbours overlap it). With 20 minutes you lose 2 of 8 windows (25 %); with 60 minutes, 2 of 28 (about 7 %).

5One graph, many islands

"How does it aggregate the results from each window?"

It doesn't, because there are no per-window results. Before training, all windows are loaded as one graph (build_graph, train_gnn_models.py:55-104). Because every node ID carries its window prefix, no edge links two windows: the graph is 8 separate islands stored in one tensor. One forward pass handles all of them, and messages never leave an island. This is the usual way to batch many small graphs in PyTorch Geometric.

The split is only a label per node, read from the prefix (:146). It doesn't change the graph; it decides which rows count for the loss (tr) and which for validation (va, :286-288). Both are torch.Tensor int64 lists of row numbers, built with np.where(mask)[0]. Purged nodes still go through the forward pass but are never selected.

The only place windows "meet": one average in the loss

The loss (:204-207) is L = r² + (1/β) · mean(relu(score)) with score = ‖emb − c‖² − r². In words: the squared distance of a node from the sphere centre c, minus the squared radius. relu(v) = max(v, 0), so only nodes outside the sphere count. The mean runs over all training nodes, whatever window they came from. β = 0.5 (PAPER §7.2.1), so 1/β = 2. Edit the scores.

nodewindowscorerelu(score)

The result is one model per node type, each with one centre c, one radius r and one threshold τ, learned from all training windows together (:298-301). τ is the (1 − contamination) quantile of the training scores (:239), with contamination 0.001 (:399, PAPER Min_con): 99.9 % of training nodes sit at or below it. With 575 training processes that leaves about 0.001 × 575 ≈ 0.6 nodes above, which is why exp01 shows 1/575 flagged.

The only real aggregation is across runs, not windows: --runs 3 trains with seeds 360, 361, 362 and reports mean ± std (:327-330). Only run 0's model is saved (:297, AUTHOR CODE l.666). That is a stability check, not a merge.

6Then why cut windows at all?

"If it trains like this, why break into 5-minute windows in the first place?"

Pooled windows are not the same as one 20-minute graph. Pooling keeps each window an island, so every node still only sees its own 5 minutes. The windows exist because live detection scores 5-minute windows, so the model must learn what normal looks like in 5-minute views. The rule: train on the same shape of data you detect on.

PAPER OCR-APT trains on a whole benign log and predicts on a whole test log, both offline, so training and test already match. OURS We detect live in 5-minute windows, so we cut training the same way (docs/DEVIATIONS.md: windowed, near-live detection).

Reason 1: idle-time features depend on the window length

Below is explorer.exe with a few events (minutes, editable). Compare its max idle gap when the 20 minutes is one graph versus when it is cut into windows.

The scaler is fitted on training values and reused live (encode_to_features.py:120-146). Toy numbers: if training were one 20-minute graph, max idle might range 0–1,100 s. A live 5-minute window can never exceed 300 s, so every live value lands in 0–0.27 of the learned range, a part the model rarely saw for long-lived processes. Normal processes start to look unusual, which means false positives. Trained on windows, the range is about 0–300 s, the same range live windows produce.

Reason 2: neighbourhoods change size

RGCN averages over a node's neighbours (RGCNConv with mean aggregation, train_gnn_models.py:183). In one 20-minute graph, chrome.exe might link to 200 files; in a 5-minute window, maybe 50. Different neighbour averages give different embeddings, so a sphere fitted to 20-minute neighbourhoods does not describe 5-minute ones. The 12 action-count features are L2-normalised (encode_to_features.py:113-117): they keep the mix of actions but not the volume, so this effect is smaller there, but the mix still shifts when a window catches only a startup burst.

Reason 3: more views, and a time-based validation split

One 20-minute graph gives one row per process; 8 windows give up to 8 views of a long-running process at different moments. They are correlated, but they show the model more variety. Holding out a time slice for validation also needs time slices. With one graph you'd fall back to a random 15 % node split (AUTHOR CODE encode_to_PyG.py l.102, noted at train_gnn_models.py:132), where validation nodes share neighbours with training nodes.

7The idle features, step by step

PAPER §5.1.2: min, max and average duration between a node's actions. idle_stats (encode_to_features.py:89-110) sorts each node's event times, takes the gaps between consecutive events, and keeps avg / max / min. Every edge's timestamp counts for both endpoints, so a file read by chrome adds an event to chrome and to the file. Then each value is min-max scaled with the training range: (value − min) / (max − min). Here the toy scaler range is 0–300 s.

Quirk. A node with one event has no gap, so all three features are set to 0 (:108-110, AUTHOR CODE l.192-196). "Seen once" then looks like "extremely busy" (gaps near 0 s). n_events tells them apart, but it is only in features_raw.csv for EDA, not a model feature.

8Pooled, yet separate

"Gaps are measured inside one window, but you said everything is combined into one graph?"

Both are true. Combined means one file and one tensor, not merged nodes. In the windowed file the same process has a different ID in each window: w0002_chrome and w0003_chrome are different strings, so they are different nodes. The idle step groups by that full ID (encode_to_features.py:97-99: ts is a pd.DataFrame with one row per (node, timestamp); ts.groupby("node_uuid") makes one group per distinct ID str, like SQL GROUP BY node_uuid), so a gap between two windows is never computed.

A backend analogy: one MongoDB collection where the $group key is (window, pid), not pid. All documents live in the same collection, but no group mixes windows. Below, chrome has four raw events; switch the grouping key.

Order of operations: the windower creates the windows and the prefixes; everything after that only ever groups by the prefixed ID. The features and the message passing both stay inside one 5-minute window, and nothing later undoes the windows.

9What this setup limits

  • Only 5 training windows. 20 minutes is not useless, it is small. The model has seen little normal behaviour.
  • Correlated rows. A long-running process appears in up to 3 overlapping windows, so there are fewer independent samples than the 6,810 rows suggest (docs/DEVIATIONS.md).
  • The first live false positive. 18 syswow64 DLLs (FILE nodes) loaded once by a short-lived updater process were flagged; training had 0 updater processes (docs/PROGRESS.md). Unseen benign behaviour is exactly what a thin capture misses.
  • Next step. Record longer or several seeded captures, keep the 5-minute window so the features stay on the live scale, retrain and recalibrate.

No number on this page is a detection metric. The training numbers say "it runs and is consistent", not "it detects attacks".
