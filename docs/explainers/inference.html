A score is just a number. Here is how it finds its node again.

At inference time the models output one number per node. This page follows that number back to a real process, file or network endpoint: who decides the node type, why the row order is never lost, and how hex IDs turn back into c:\windows\system32\wuuhext.dll.

The short answer: identity never passes through the model. The converter fixes each node's type and ID when it reads the raw ETW event. After that, every array keeps the same row order as a node table, and the scores are joined back by ID.

Real rows on this page come from live session live-20261011T112141Z, window 20261011T113000Z (src/live/sessions/, not in git): 717 nodes (129 process, 396 file, 192 net), 7 flagged. 2The converter decides the type and the ID

OURS The node type comes from which ETW event created the node (etw2nodlink.py, classify at :76). The ID is built so the same thing gets the same ID in training, test and live (CLAUDE.md §9, node identity):

  • PROCESS: p<pid>_<start ms> from ProcessStart (:199). PIDs get reused, so the start time is part of the key. A process already running when capture began has no start event and gets p<pid>_pre_<run> (:149-155).
  • FILE: f + the first 16 hex characters of SHA-1(lower-cased path) (:157-158, used by Load :213 and Read/Write :232).
  • NET: n + the first 16 hex characters of SHA-1(daddr:dport) as SilkETW writes them (:247).

SHA-1 can't be reversed, so the converter also writes a lookup table, node_attrs.csv (node, node_type, node_attr, :16). Pick an event and edit it; the IDs are computed live with the same SHA-1.

Leave "its start" empty to see the _pre_ ID of a process that started before the capture. The defaults reproduce real rows from the session: p5568_1791718201999 (wuauclt) loading feb89e175ed137cbd.

3One node table, many arrays, the same row order

build_graph (train_gnn_models.py:55-104) builds the node table from the two ID columns of the edges, together with the type column next to each ID. Row i of that table is node i. The features are reindexed to that order (score_window.py:98), and the model returns embeddings and scores in that same order. Nothing ever re-sorts them. Click any cell: the same row lights up everywhere.

A backend analogy: the arrays are projections of one table that keep its row order. The scores come back as an array; you zip it with the ID column, the way you'd zip a batch response with the batch request.

4Three models, one mask each

There is one OCRGCN per node type. In score_edges (score_window.py:104-110) each model runs its encoder on all nodes, because a file's embedding depends on the processes around it (PAPER §5.1.2). It then keeps only the scores on rows of its own type, using a True/False mask is_t:

Nothing is guessed or reconstructed: if an ID is in the window's edges, its attribute is in attrs. When the converter never learned a name, the value is "unknown" (engine.py:309).

6NET values are decoded for the screen only

SilkETW writes an IPv4 address and port as signed integers with thousands separators, for example 186,428,310:-17663. decode_net_attr (alg2.py:235-249) turns them into a.b.c.d:port. The address is the 4 bytes of the integer read little-endian (lowest byte first); the port is 2 bytes in network order, so its bytes are swapped. The UI shows both values (display_attrs, engine.py:112-117); stored files and node IDs keep the raw value, so the hash still matches.

10.0.2.15 is the VM's own address on the VirtualBox NAT network, so the flagged NET node above is a connection from the VM itself, not an outside host.

7The model never sees the ID

The ID only picks which row a node's features go in. The model's input is the 15 behaviour features and the edges, never the ID string. That's why a file whose hash never appeared in training can still be scored: its features say how it behaved in this window, and the model judges that behaviour.

Two edge cases on the way in:

  • An edge whose (source type, action, destination type) triple never appeared in training has no learned weight, so it is dropped with a warning (train_gnn_models.py:68-75). It is counted as edges_dropped_relation.
  • A node that lost all its edges that way still keeps its row, with zero features (score_window.py:99-100), counted as nodes_without_features.

8From flagged IDs to an alert

Alg. 1 (alg1.py:77, called at engine.py:349) starts from the flagged IDs, takes the edge rows of the same window that touch them (:91-95), and grows subgraphs. Because it works on the same IDs, every subgraph node already carries its type and its name. In this window the first subgraph is:

subgraph 0 seed fe62c25f6e22f0b29 score 2.0 level Minor kept: no process wuauclt connector (not flagged, links the two) file c:\windows\system32\wuauclt.exe anomalous file c:\windows\system32\wuuhext.dll anomalous

Read as a sentence: "wuauclt loaded wuuhext.dll and its own image, both unusual". With a score of 2.0 it stays below our Moderate cut-off of 30 (OURS, DEVIATIONS), so the window stays green. How subgraph scores and levels work is on the live windows page.

9Where the mapping is weaker

  • Processes started before capture have no start time, so their ID is p<pid>_pre_<run>: stable within one run, but not across runs.
  • Missing names. A process seen only through its PID can have an empty name until an event supplies one; then attr is "unknown".
  • File I/O without a known path (file opened before capture) is not turned into an edge at all (etw2nodlink.py:228-231), so that node never exists.
  • NET decoding is IPv4 only. Anything else is shown unchanged (alg2.py:239-241).
