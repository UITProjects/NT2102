=====================================================

Q1. Vì sao dùng RGCN mà không dùng GNN thường (GCN)?
----------------------------------------------------
Trả lời ngắn: vì loại edge mang nghĩa. GCN dùng chung MỘT trọng số W cho mọi neighbor, nên
"rundll32 Load stage.dll" và "một process Write stage.dll" bị nhân cùng một trọng số, dù với
người phân tích bảo mật đây là hai hành vi khác hẳn. RGCN có một trọng số W_r riêng cho mỗi
loại edge (Write, Read, Send, Recv, Start, Load), mô hình tự học mỗi loại "kéo" bao nhiêu.
[PAPER §5.1.1: RGCN "incorporating edge types during the embedding aggregation process"]

Ví dụ (feature chỉ 1 số, cùng số với slide animation một lớp RGCN):
  rundll32 h = 1, stage.dll h = 2, kernel32.dll h = 4, flow 203.0.113.50 h = 10
  W_0 = 0.5 (chính nó), W_load = -0.2, W_write = 0.1, W_send = 0.02

                       chính nó    2 file (trung bình 3)    flow             kết quả
  Load (thật)          0.5 * 1     3 * (-0.2) = -0.6        10 * 0.02 = 0.2   0.1
  Write (giả sử)       0.5 * 1     3 * 0.1    =  0.3        0.2               1.0

Cùng neighbor, cùng feature, chỉ khác loại edge -> biểu diễn khác (0.1 so với 1.0).
Với GCN (một W chung) hai trường hợp ra cùng một số, nên mô hình không phân biệt được.


Q2. Mỗi lớp RGCN "nhìn xa" bao nhiêu? (ví dụ rundll32, vết 17 event ở ②)
-------------------------------------------------------------------------
Mỗi lớp nhìn xa thêm 1 bước trên đồ thị:
  1 bước: powershell (start rundll32), stage.dll, kernel32.dll, flow 203.0.113.50
  2 bước: stage.dll do chính powershell ghi ra; flow đó powershell cũng dùng; kernel32.dll chrome cũng nạp
  3 bước: invoice.docm, explorer, chrome (đã tải invoice.docm)
Sau 3 lớp, embedding Z của rundll32 mang thông tin từ cả chuỗi:
  tài liệu -> powershell -> thả DLL -> rundll32 nạp -> gửi ra ngoài.
[PAPER §7.2.1: 3 lớp RGCN, 32 chiều]


Q3. Vì sao có 12 quan hệ, không phải 6?
---------------------------------------
6 loại edge (Write, Read, Send, Recv, Start, Load) + 6 quan hệ ngược (inv_load, inv_send, ...).
Thông điệp chỉ chạy theo chiều edge (source -> destination). Edge "rundll32 Load stage.dll" chỉ đưa
thông tin từ rundll32 sang stage.dll; quan hệ ngược inv_load cho chiều kia, nên rundll32 cũng nhận
được thông tin từ stage.dll mà nó nạp.
[AUTHOR CODE: mã gốc thêm "inv_<rel>" cho mỗi bộ ba; đồ án giữ nguyên, src/pipeline/train_gnn_models.py
 lưu quan hệ ngược dạng "dst|inv_rel|src"]

Q5. Cho ví dụ có số của message passing (slide "③ GNN: message passing")
-------------------------------------------------------------
Mỗi node 1 số cho dễ tính; w_self = 0.5, w_nb = 1.
A có h_A = 2, neighbor B, C, D = 4, 0, 1 -> mean = 5/3 ≈ 1.67
  h'_A = ReLU(0.5·2 + 1·1.67) = ReLU(2.67) = 2.67
Nếu neighbor là -6, -2, -1 -> mean = -3
  h'_A = ReLU(1 - 3) = ReLU(-2) = 0
Cùng node A, khác neighbor -> khác vectơ mới. Ví dụ đầy đủ với loại edge: slide rundll32 (RgcnLayer).


Q6. Vì sao không xếp 10 lớp cho nhìn xa hơn?
---------------------------------------------
Mỗi lớp lấy trung bình với neighbor. Xếp quá nhiều lớp thì vectơ của mọi node bị trộn đến mức gần
giống nhau (over-smoothing: mọi màu trộn thành cùng một màu xám), nên
không còn phân biệt được node bất thường. OCR-APT dùng 3 lớp [PAPER §7.2.1]: đủ thấy chuỗi
process -> file -> process -> mạng.

  behavior feature (đếm hành động), không đưa tên/IP vào mô hình.

Q-L2. Ví dụ số: chuẩn hoá L2 và min-max (slide behavior feature)
----------------------------------------------------------------
L2 (chia hàng cho độ dài Euclid ‖a‖ = √(a1² + … + a12²)) — giữ TỈ LỆ giữa các action, bỏ độ bận:
- chrome: counts (write 1, send 2, recv 3, start_in 1, load 1) -> ‖a‖ = √(1+4+9+1+1) = √16 = 4
  -> out_recv = 3/4 = 0.75, out_send = 2/4 = 0.5, out_write = 1/4 = 0.25.
- Browser bận: send 300, recv 400 -> ‖a‖ = 500 -> (0.6, 0.8). Lúc rảnh: 3, 4 -> ‖a‖ = 5 -> (0.6, 0.8):
  CÙNG hành vi, CÙNG feature, dù khối lượng khác 100 lần. Đó là ý nghĩa "bỏ độ bận, giữ tỉ lệ".

Min-max cho 3 cột thời gian nghỉ ((x − min)/(max − min), min/max lấy từ scaler fit trên TRAIN):
- Train max nghỉ = 290 s (bằng độ dài window trừ chút). Một node nghỉ 145 s -> 145/290 = 0.5.
- Node nghỉ 300 s lúc test/live -> 300/290 = 1.03, VƯỢT [0,1] — bình thường, vì thang cố định theo train
  (DEVIATIONS D3). rundll32 im 214 s giữa hai lần hoạt động -> cột max nghỉ ≈ 0.99, gần kịch trần.

Q10. Hidden layer là gì? Kích thước tensor qua các lớp?
--------------------------------------------------------
Hidden layer = vectơ của node SAU mỗi lớp RGCN, do mô hình tự tính, không có trong log.
  X [N, 15] -> H1 [N, 32] -> H2 [N, 32] (-> H3 [N, 32]) = Z (embedding)
Lớp đầu W_r [15, 32], các lớp sau [32, 32]. Lớp cuối không qua ReLU nên Z có thể âm.
OCR-APT dùng 3 lớp [PAPER §7.2.1]; exp08 dùng 2 lớp (nông hơn, bớt nhạy với nhiễu ngữ cảnh).
Chỉ Z đem vào hypersphere. Hình minh hoạ: báo cáo §2.3.


Q11. Điểm subgraph tính thế nào? Vì sao mốc Moderate = 10?
-----------------------------------------------------------
Điểm thô s_i khác thang giữa các loại node (NET có thể âm), nên cộng xác suất min-max đã kẹp:
  p_i = clamp((s_i - s_min_train) / (s_max_train - s_min_train), 0, 1),  score(sg) = Σ p_i (node bị cờ)
Ví dụ FILE có điểm train trong [0.10, 0.23]:
  file s = 0.32  -> (0.32 - 0.10)/0.13 = 1.69 -> kẹp p = 1
  file s = 0.165 -> (0.165 - 0.10)/0.13 = 0.5
Vì p <= 1: điểm >= 10 ⇔ ít nhất ~10 anomalous node trong một câu chuyện liên thông.
Thang: Minor < 10, Moderate 10–100, Significant 100–1000, Critical > 1000 [PAPER §7.2.1].
[AUTHOR CODE] dùng > 10 và top-k khi không có gì đạt; đồ án bỏ top-k (live thì mọi window sẽ đỏ).
Mốc [OURS] 30 cũ đã bỏ 2026-11-03 (D8). Báo cáo: Phụ lục, mục Thuật toán 1.
