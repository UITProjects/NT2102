Seventeen events become nine rows of numbers

A walk through feature_engineering() in encode_to_PyG.py for the SimulatedW10 host. It starts from what transform_to_RDF.py writes and ends at the out_<action> / in_<action> columns that become the node tensors. The input is a small simulated Windows trace: a download, a macro that spawns PowerShell, and a rundll32 that beacons out.

chrome.exeRecv198.51.100.23:443t = 1791428403150
x_list["proc-3c51"]["out_recv"] += 1 x_list["flow-4b2c"]["in_recv"] += 1

That is the whole idea. Every event adds 1 to a counter on its source node and 1 to a counter on its destination node. The rest of this page shows where those counters come from, what happens to them afterwards, and what is lost along the way.

Tags: REPO verified in the project's repo files, with file and line. PAPER stated in the paper. INFERENCE an interpretation, not verified in code or paper. IMPL a practical note for anyone re-implementing this step.

0Where this step sits

Audit log→NODLINK-format edge CSV→transform_to_RDF.py→encode_to_PyG.py · feature_engineering()→node-features.pt→OCRGCN

PAPER §5.1.2 describes two behavior features: action frequencies (the proportion of each action type in a node's activity, L2-normalized) and idle-period statistics. This page covers only the first one, the action columns. Timestamps also get summarized into node features, as min/max/avg idle time (encode_to_PyG.py l.149–201), but that is a separate topic.

1Two files come in, only one gets counted

REPO transform_to_RDF.py writes two files that encode_to_PyG.py reads back (l.269–271):

<graph>.tsv holds RDF triples (subject, predicate, object), built at transform_to_RDF.py l.133–223. The encoder uses it to discover node types (l.276), declared edge types (l.277), the per-type node index (l.306–340), labels and the train/test split.

<graph>_graph_df.csv is the plain edge table, one row per event, saved at transform_to_RDF.py l.390. Despite the .csv name it is tab-separated. This is the file the action counts are computed from (l.510 passes graph_df into feature_engineering).

The plain triples have no timestamps. A triple like node/A  Start  node/B is a set member, so two identical events would collapse into one. The counts only work because graph_df keeps every event as its own row.

Highlighted columns are read in the counting loop. timestamp is read too but only feeds the idle features. The column order here is illustrative: the code looks columns up by name (l.138). Node types PROCESS / FILE / NET match the NODLINK names in database_config.py l.106. INFERENCE Edge direction (process as subject for Recv and Load) is an assumption of this simulation and has not been verified against NODLINK's raw data.


      
Highlighted triples are what the encoder pulls out. Edge-type declarations look like Write a …/edge-type (transform_to_RDF.py l.214–215), and l.277 collects their subjects. For W10 that list is then ignored, as section 2 explains. The node-attribute values (image names, paths, IPs) never reach the features. PAPER §5.1.1 leaves them out on purpose so the model does not memorize specific instances.

    What to notice once all 17 are in
    
      
    INFERENCE In this schema every event has a process as its subject, so out_* counters only ever fill on process rows. File and flow rows get only in_* counters. Start is the one action where a process sits on both sides, which is why processes have both out_start and in_start. So the 12 columns are shared by every node, but each node type actually uses a different subset of them.
    
      
    The counts carry three things: how much of each action a node did, in which role (source or target), and nothing else. Who the counterpart was is gone. out_send = 2 on chrome does not say which flow. The order is gone too: the table cannot distinguish "write stage.dll, then rundll32 loads it" from the reverse. In OCRGCN, the counterpart is recovered later by message passing over edge_index, and the order by the LLM stage, which serializes events by timestamp.

    Feature width now: 
    
    
    
    
    
    
    
      
    Why this matters for per-window encoding. IMPL The repo encodes the training and test logs together as one graph (is_Train just labels the nodes), so the columns that survive are always the same for both. If a pipeline encodes each time window on its own, a quiet window with no Load events comes out 10 columns wide. A model trained on 12 columns then either fails on a shape mismatch or, if two different columns happen to drop, silently reads the wrong ones. For per-window encoding, keep the fixed 12-column list and skip l.204.
    
    
    
  
    

    


    
  
    
    
    5Counts become a behavior mix
    
    
    
      
    PAPER §5.1.2 uses L2 normalization "to reduce bias from high-activity benign nodes". REPO With --normalize-features, each row of action columns is divided by its own Euclidean length:
    
    
    

        if args.normalize_features:        sorted_edge_types = [action for action in sorted_edge_types if action in x_list_df.columns]        normalized_data = normalize(x_list_df[sorted_edge_types], norm='l2', axis=1)        normalized_x_list_df[sorted_edge_types] = pd.DataFrame(normalized_data, columns=sorted_edge_types)
    
    
    encode_to_PyG.py l.226–234 (axis=1 means per row, so per node)
    
    
    
      
    For node $i$ with count vector $c_i \in \mathbb{R}^{F}$:
    
      
    $$\tilde{c}_i = \frac{c_i}{\lVert c_i \rVert_2}, \qquad \lVert c_i \rVert_2 = \sqrt{\textstyle\sum_{k=1}^{F} c_{ik}^2}$$
    
      
    Each row now has length 1, so it describes the node's mix of actions, not how busy it was. Scaling all of a node's counts by 100 gives exactly the same row. Click any row in the table to see its arithmetic.
    
    
    
    
    
    
    
    
    
      
    Compare explorer.exe and rundll32.exe. Explorer did only one thing (Start twice), so its single non-zero cell becomes 1.0. Two of rundll32's 4 counted actions were loads, so its out_load is 0.816, larger than chrome's 0.25 even though chrome had just 1 fewer load. After normalization, a value only means something relative to the rest of the same row.

    ?Check yourself
    
    
    1. After L2, rundll32's out_load is 0.816 and chrome's is 0.25. Does that mean rundll32 loaded about three times as much?
      
    No. Raw counts are 2 and 1. The normalized value is the share of that action in the node's own mix: rundll32 did only 4 actions, chrome did 8 spread over 5 columns. Comparing the same column across rows compares behavior profiles, not volumes.
    
    
    
    
    2. Remove all Load events: F drops to 10. Why doesn't the repo's own pipeline ever hit this, while an encoder that processes each time window separately can?
      
    The repo encodes training and test logs as one graph, so the zero-column check sees both together and keeps the same columns for both. Separate per-window encodings each run l.204 on their own data, so a window without Load produces a narrower tensor than the model was trained on.
    
    
    
    
    3. In this schema, can a FILE node ever have a non-zero out_ value? What does that say about how informative the 12 columns are per type?
      
    Not if every event has a process as its subject. File and flow rows only use the in_* half (in this data, at most 3 of the 12 columns). The per-type OCRGCN models (§5.1.2) each see a sparse slice of the shared feature space, which is one reason the GNN's neighbor aggregation matters so much for non-process nodes.
